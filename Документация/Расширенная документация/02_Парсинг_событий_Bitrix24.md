# Парсинг событий Bitrix24

Модуль `events.py` реализует сложную логику извлечения данных из разнородных форматов payload, которые Bitrix24 отправляет в разных версиях API и через разные каналы.

---

## Проблема: непоследовательность форматов

Bitrix24 не гарантирует единообразный формат payload. Одно и то же поле может прийти как:
- `dialogId` (camelCase)
- `DIALOG_ID` (UPPER_SNAKE_CASE)
- `dialog_id` (lower_snake_case)

Кроме того, структура payload отличается между push-уведомлениями и REST webhook.

---

## Вспомогательные функции

### `_lookup()` — case-insensitive поиск ключа

Выполняет трёхпроходный поиск в словаре:
1. Точное совпадение (`key`)
2. По нижнему регистру (`key.lower()`)
3. По верхнему регистру (`key.upper()`)

Это покрывает все известные варианты написания ключей от Bitrix24.

**Строка кода:** `events.py:23-31`

---

### `_resolve()` — навигация по вложенным путям

Проходит по пути из кортежа ключей, на каждом уровне используя `_lookup()`. Возвращает `None` при отсутствии любого промежуточного ключа.

Пример: `_resolve(data, ("data", "chat", "dialogId"))` безопасно спускается на три уровня вложенности.

**Строка кода:** `events.py:34-40`

---

### `_iter_listish()` — полиморфная обработка списков

Bitrix24 возвращает списки в трёх форматах:

| Формат | Пример | Поведение |
|--------|--------|-----------|
| JSON-массив | `[{...}, {...}]` | Возвращается как есть |
| Словарь с числовыми ключами | `{"0": {...}, "1": {...}}` | Извлекается как список, отсортированный по ключам |
| Словарь с текстовыми ключами | `{"msg": {...}}` | Оборачивается в список из одного элемента |

Первый формат — стандартный JSON. Второй — результат PHP-сериализации, который Bitrix24 иногда возвращает. Третий — когда элемент не является списком по смыслу.

**Строка кода:** `events.py:11-20`

---

### `_first_str()`, `_first_int()`, `_first_bool()` — мульти-path извлечение

Каждая функция перебирает несколько кандидатов-путей и возвращает первое валидное значение:

- **`_first_str`** — пропускает `None` и пустую строку, приводит к `str()`
- **`_first_int`** — пропускает `None`, пустую строку и значения, которые не конвертируются в `int()`
- **`_first_bool`** — обрабатывает нативный `bool`, строки `"1"/"true"/"y"/"yes"` (регистронезависимо), по умолчанию `False`

**Строки кода:** `events.py:181-210`

## Двойной источник данных

Bitrix24 отправляет события через два канала с разной структурой:

1. **Push-уведомления** — данные на верхнем уровне payload: `("dialogId",)`, `("message", "text")`
2. **REST webhook** — данные вложены в `raw_data`: `("PARAMS", "DIALOG_ID")`, `("data", "PARAMS", "MESSAGE")`

Каждое поле `IncomingEvent` извлекается посредовательно из обоих источников. Если в первом источнике ничего не найдено, используется второй.

Пример для `dialog_id` — перебирается 8 путей из двух источников:

**Payload:**
- `("dialogId",)`
- `("chat", "dialogId")`
- `("data", "chat", "dialogId")`
- `("chat", "dialog_id")`

**raw_data:**
- `("PARAMS", "DIALOG_ID")`
- `("data", "PARAMS", "DIALOG_ID")`
- `("dialogId",)`
- `("chat", "dialogId")`

**Строки кода:** `events.py:70-85`

---

## Эвристика извлечения bot_id

Блок `BOT` в raw_data может иметь нестандартный формат:

```json
{"BOT": {"123": {"NAME": "My Bot"}}}
```

Здесь bot_id — ключ словаря, а не значение поля. Детектор проверяет:
1. Если `BOT` — словарь ровно с одним ключом → ключ интерпретируется как bot_id
2. Если `BOT` — словарь с несколькими ключами → ищет `id`/`ID` внутри

**Строки кода:** `events.py:167-178`

## Строгая vs мягкая валидация

### Мягкая (OpenLineMessage)

Парсер `_parse_openline_message` извлекает все поля, но не отбрасывает сообщения при отсутствии обязательных. Поля типа `chat_id`, `message_id` могут быть `None` — это обрабатывается на этапе фильтрации в handler.

**Строки кода:** `events.py:325-353`

### Строгая (ConnectorMessage)

Парсер `_parse_connector_message` **отклоняет** сообщения, где `chat_id`, `im_chat_id` или `im_message_id` равны `None`. Это требование протокола коннекторов — все три ID обязательны для доставки.

**Строки кода:** `events.py:356-379` (особенно строка 370-371)
