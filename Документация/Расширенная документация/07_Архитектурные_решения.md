# Архитектурные решения

Документ описывает обоснование ключевых архитектурных решений проекта — почему компоненты устроены именно так, а не иначе.

---

## Два HTTP-клиента

### Ситуация

Проект использует два разных механизма для HTTP-запросов:

| Клиент | Модуль | Тип | Использование |
|--------|--------|-----|---------------|
| `fast_bitrix24.Bitrix` | `bitrix_client.py` | Async | REST webhook-вызовы от имени бота |
| `urllib.request.urlopen` | `oauth_client.py`, `handlers.py` | Sync | OAuth-операции, внешние вебхуки |

### Обоснование

- **`fast-bitrix24`** — специализированная библиотека для Bitrix24 REST API. Автоматически обрабатывает rate-limit (ограничения на количество запросов), пакетирует вызовы, поддерживает асинхронность. Идеально подходит для бота, который может отправлять много сообщений.
- **`urllib.request`** — стандартная библиотека Python. Используется для OAuth-операций (редкие вызовы, не требующие rate-limit) и внешних вебхуок (один запрос на сообщение). Простота и отсутствие зависимостей.

### Lazy init BitrixClient

Клиент инициализируется в `__post_init__`. Если `rest_webhook_url` пуст, `_client` остаётся `None` и все методы выбрасывают `RuntimeError`. Это позволяет запустить приложение без webhook URL (только для Open Lines через OAuth).

**Строки кода:** `bitrix_client.py:16-20`

## Frozen Settings

`Settings` в `config.py` создаётся с `frozen=True`:

```python
@dataclass(frozen=True, slots=True)
class Settings:
    ...
```

### Обоснование

- Конфигурация не должна изменяться после инициализации
- Замороженный dataclass невозможно изменить случайно
- Гарантирует, что все компоненты видят одни и те же значения на протяжении всей жизни приложения
- Потокобезопасность по умолчанию (нет мутабельного состояния)

**Строка кода:** `config.py:9`

## Мультиплексор webhook

Endpoint `/webhooks/bitrix24/app/{secret}` обрабатывает два типа событий через один маршрут:

```python
if event_type == "ONAPPINSTALL":
    result = app_install_handler.handle(event)
if event_type == "ONOPENLINEMESSAGEADD":
    result = openlines_handler.handle(event)
```

### Обоснование

Bitrix24 отправляет события `ONAPPINSTALL` и `ONOPENLINEMESSAGEADD` на один URL. Это единственный endpoint, который приложение может зарегистрировать через `event.bind`. Мультиплексор dispatches по полю `event` в payload.

**Строки кода:** `app.py:196-225`

## HandleResult — структурированный результат

Все обработчики возвращают `HandleResult`:

```python
@dataclass(slots=True)
class HandleResult:
    handled: bool
    reason: str
    echoed_text: str | None = None
```

### Обоснование

- Разделяет бизнес-логику (handler) и HTTP-слой (app.py)
- API-слой преобразует `reason` в HTTP-ответ: `"invalid_application_token"` → 403, остальное → 200
- `reason` используется для логирования и мониторинга
- `echoed_text` опционален — только для echo-бота

**Строки кода:** `handlers.py:16-20`, `app.py:156-157`

## AppAuth.from_mapping() — defensive typing

```python
@classmethod
def from_mapping(cls, data: dict[str, Any]) -> "AppAuth":
    return cls(
        access_token=str(data.get("access_token", "")),
        refresh_token=str(data.get("refresh_token", "")),
        ...
    )
```

### Обоснование

Bitrix24 может вернуть `None`, отсутствующие ключи или неожиданные типы. Метод `from_mapping()` гарантирует, что:
- Все поля — строки (никогда `None`)
- Отсутствующие ключи → пустая строка
- Вызывающий код может безопасно использовать любое поле без проверки на `None`

**Строки кода:** `app_auth.py:20-30`

## Event multiplexing в app webhook

App webhook (`/webhooks/bitrix24/app/{secret}`) — единственный endpoint, который Bitrix24 может привязать через `event.bind` для `ONOPENLINEMESSAGEADD`. Поэтому он же обрабатывает `ONAPPINSTALL`.

### Схема диспатча

```
Входящий payload
  │
  ├─ event == "ONAPPINSTALL"
  │   → AppInstallHandler.handle()
  │
  ├─ event == "ONOPENLINEMESSAGEADD"
  │   → OpenLineMessageHandler.handle()
  │
  └─ другой event
      → {"handled": false, "reason": "ignored_event:..."}
```

## Отдельные обработчики для разных каналов

### Почему два обработчика Open Lines

| Обработчик | Вход | Выход | Использование |
|-----------|------|-------|---------------|
| `OpenLineMessageHandler` | ONOPENLINEMESSAGEADD | imopenlines.bot.session.message.send | App webhook |
| `OpenLinesConnectorHandler` | ONIMCONNECTORMESSAGEADD | imconnector.send.messages | Connector webhook |

`OpenLineMessageHandler` работает с сессиями Open Lines и вызывает внешний сервис для генерации ответа. `OpenLinesConnectorHandler` работает с коннекторами и отправляет эхо-ответ напрямую через коннекторный API.

## In-memory дедупликация vs持久化

### Почему in-memory

- Дубликаты приходят в течение секунд (не минут/часов)
- Бот — stateless процесс, перезапуск сбрасывает историю
- Persistent storage потребует внешней зависимости (Redis, БД)
- Для масштабирования (multiple instances) потребуется shared storage — это отдельная задача

### Когда это может стать проблемой

- Горизонтальное масштабирование (несколько экземпляров бота)
- Долгое время работы без перезапуска (>10,000 событий)
- Требование exactly-once обработки

В текущей конфигурации in-memory решение оптимально по соотношению сложность/эффективность.
