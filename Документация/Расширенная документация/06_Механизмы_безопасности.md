# Механизмы безопасности

Проект реализует несколько уровней защиты: валидацию секретов webhook, санитизацию логов и валидацию токенов приложения.

---

## Валидация секрета webhook

### Принцип

Каждый из трёх webhook-эндпоинтов содержит секрет в URL: `/webhooks/bitrix24/{secret}`. Секрет сравнивается со значением из `BITRIX_INBOUND_SECRET`.

### HTTP 404 вместо 401/403

При несовпадении секрета бот возвращает **HTTP 404 Not Found**, а не 401 или 403. Это намеренное решение:

- **401 Unauthorized** — раскрывает факт существования защищённого ресурса
- **403 Forbidden** — раскрывает факт аутентификации
- **404 Not Found** — для злоумышленника ресурс не существует

**Строки кода:** `app.py:92-93`, `app.py:137-138`, `app.py:185-186`

### Диагностическое логирование

В логах записываются последние 4 символа как полученного, так и ожидаемого секрета. Это помогает при отладке (опечатки в URL) без раскрытия полного секрета.

```python
"secret_suffix": secret[-4:] if secret else "",
"expected_secret_suffix": settings.inbound_secret[-4:] if settings.inbound_secret else "",
```

**Строки кода:** `app.py:86-89`

### Замечание о timing-safe сравнении

Используется стандартное сравнение строк (`!=`), а не constant-time сравнение. Для модели угрозы валидации webhook от Bitrix24 это допустимо — атакующий не может эксплуатировать timing side-channel через webhook URL. Если проект будет расширяться на публичные API с высокими требованиями к безопасности, стоит рассмотреть `hmac.compare_digest()`.

## Санитизация логов

### Механизм

Функция `_sanitize_for_log()` рекурсивно обходит все данные перед записью в лог. Любое значение с ключом из `_SENSITIVE_KEYS` заменяется на `"***"`.

**Строки кода:** `app.py:30-38`, `oauth_client.py:26-34`

### Маскируемые ключи

| Ключ | Где встречается |
|------|----------------|
| `auth` | REST-запросы к Bitrix24 |
| `access_token` | OAuth-ответы |
| `refresh_token` | OAuth-ответы |
| `client_secret` | Конфигурация |
| `bot_token` | Конфигурация |
| `token` | Общее |
| `application_token` | События приложения |

### Трёхуровневая рекурсия

Функция обрабатывает:
1. **Словари** — проверяет каждый ключ, рекурсивно обходит значения
2. **Списки** — рекурсивно обходит каждый элемент
3. **Скаляры** — возвращает как есть

### Где применяется

- Исходящие webhook-запросы от Bitrix24 (входящие payloads)
- Исходящие REST-запросы через OAuth-клиент (содержат `auth` токен)

**Строки кода:** `app.py:101`, `app.py:146`, `oauth_client.py:83`, `oauth_client.py:111`

## Валидация токена приложения

### Двухслойная проверка

Приложение может быть установлено до настройки бота. В этом случае `application_token` ещё не сохранён. Бот обрабатывает это корректно:

1. Загружает `AppAuth` из файла
2. Если файл существует и содержит `application_token` — проверяет соответствие
3. Если файла нет или `application_token` пуст — пропускает проверку

### Где применяется

- `OpenLinesConnectorHandler.handle()` — строка 119-125
- `OpenLineMessageHandler.handle()` — строки 285-288

## Защита токенов при хранении

### Файл токенов

Токены приложения хранятся в JSON-файле по пути `BITRIX_APP_STATE_PATH`. Файл:
- Не попадает в git (`.gitignore` должен содержать `.bitrix/`)
- Создаётся автоматически с `mkdir(parents=True, exist_ok=True)`
- Записывается с `indent=2` для читаемости и `ensure_ascii=False` для Unicode

**Строки кода:** `app_auth.py:45-48`

### Потокобезопасный доступ

`AppAuthStore` использует `threading.Lock` для защиты от гонок при чтении/записи файла.

**Строки кода:** `app_auth.py:36`, `app_auth.py:39`, `app_auth.py:46`
