# Конвейер обработки Open Lines

Каждое входящее сообщение Open Lines проходит через 7-ступенчатый конвейер фильтрации и обработки. На каждом шаге сообщение может быть отклонено. Реализация: `handlers.py`, метод `OpenLineMessageHandler.handle()`.

---

## Этап 1: Проверка типа события

Фильтр пропускает только события с типом `ONOPENLINEMESSAGEADD`. Все остальные типы отклоняются с результатом `ignored_event:{тип}`.

**Строка кода:** `handlers.py:282`

---

## Этап 2: Валидация application_token

Загружает сохранённый `AppAuth` из файла через `AppAuthStore.load()`. Если токен сохранён ранее, входящий `event.application_token` должен ему соответствовать. Если файл ещё не существует (приложение не установлено), проверка пропускается — `expected_token` остаётся пустой строкой.

**Строки кода:** `handlers.py:285-288`

---

## Этап 3: Дедупликация каждого сообщения

Каждое сообщение в пакете проверяется индивидуально. Ключ дедупликации формируется из пяти полей через разделитель `:`:

```
event_type:connector_id:line_id:chat_id:message_id
```

Это означает, что один и тот же пакет может содержать как обработанные, так и пропущенные (дубликаты) сообщения.

**Строки кода:** `handlers.py:292-304`, формирование ключа: `handlers.py:445-446`

---

## Этап 4: Отсев системных сообщений

Сообщения с флагом `is_system` или с `message_user_id` равным `None` или `0` отбрасываются. Это предотвращает ответы на внутренние уведомления Bitrix24: «посетитель присоединился», «оператор сменён» и т.п.

**Строки кода:** `handlers.py:306-320`

---

## Этап 5: Отсев сообщений от операторов

Если `message_user_id` не равен `connector_user_id`, сообщение отправлено внутренним оператором или ботом на стороне коннектора, а не внешним посетителем. Бот пропускает такие сообщения, чтобы избежать бесконечного эхо-цикла между коннекторами.

**Строки кода:** `handlers.py:322-339`

---

## Этап 6: Разрешение dialog_id через внешний API

Самый сложный этап. Для отправки ответа боту нужно знать `chat_id` сессии. Если в сообщении есть `connector_id`, `line_id`, `connector_chat_id` и `message_user_id`, бот пытается разрешить реальный `chat_id` через вызов `imopenlines.dialog.get`.

### Формирование user_code

Строится составной код из четырёх полей через разделитель `|`:

```
{connector_id}|{line_id}|{connector_chat_id}|{message_user_id}
```

### Вызов API и обработка ответа

Ответ API проверяется на наличие `result.id` или `result.ID` (Bitrix24 использует разный регистр ключей). Если получен положительный целочисленный `resolved_chat_id`, он заменяет `target_chat_id`.

### Поведение при ошибке

Весь блок разрешения обёрнут в `except Exception`. Любая ошибка API приводит к молчаливому fallback на `connector_chat_id` или `chat_id` из сообщения.

**Строки кода:** `handlers.py:357-387`

---

## Этап 7: Отправка ответа и логирование

После прохождения всех фильтров:

1. Текст сообщения отправляется во внешний сервис (`_request_external_answer`)
2. Ответ внешнего сервиса отправляется пользователю через `imopenlines.bot.session.message.send`
3. Вызывается `imopenlines.session.history.get` (только для логирования)
4. Ключ дедупликации добавляется в хранилище

**Строки кода:** `handlers.py:414-441`

---

## Протокол валидации ответа внешнего сервиса

Метод `_request_external_answer` (`handlers.py:223-265`) выполняет три проверки ответа:

1. **Непустой ответ** — если тело ответа пустое после strip, выбрасывается `RuntimeError`
2. **Валидный JSON** — если ответ не парсится как JSON, выбрасывается `RuntimeError` с указанием сырого текста
3. **Строковое поле `output`** — ключ `output` должен присутствовать и быть строкой. Если его нет или это не строка — `RuntimeError`

Любой `RuntimeError` всплывает в webhook-обработчик и превращается в HTTP 500.

**Строки кода:** `handlers.py:254-264`

---

## Конвейер в виде схемы

```
Входящее сообщение
  │
  ├─ [Этап 1] Тип != ONOPENLINEMESSAGEADD? ──→ ignored_event
  │
  ├─ [Этап 2] application_token не совпадает? ──→ invalid_application_token
  │
  ├─ [Этап 3] Уже было? ──→ duplicate_event
  │
  ├─ [Этап 4] Системное сообщение? ──→ пропуск (continue)
  │
  ├─ [Этап 5] От оператора? ──→ пропуск (continue)
  │
  ├─ [Этап 6] Пустой текст? ──→ пропуск (continue)
  │
  ├─ [Этап 7] Разрешение dialog_id ──→ fallback при ошибке
  │
  └─ Ответ → внешний сервис → пользователю → дедуп → лог
```
