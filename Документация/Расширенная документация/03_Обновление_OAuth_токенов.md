# Обновление OAuth токенов

`OAuthBitrixClient` реализует автоматическое обновление access-токена при получении HTTP 401 от REST API Bitrix24. Механизм прозрачен для вызывающего кода — при каждом вызове `call()` клиент гарантирует валидный токен.

---

## Точка вызова

Все REST-вызовы от имени приложения проходят через метод `call()`:

```python
result = oauth_client.call("imopenlines.bot.session.message.send", {...})
```

**Строка кода:** `oauth_client.py:74-132`

---

## Токен в запросе

Access-токен инжектируется в payload каждого запроса под ключом `auth`:

```python
payload = {**params, "auth": auth.access_token}
```

**Строка кода:** `oauth_client.py:78`

---

## Обработка HTTP 401

### Шаг 1: Обнаружение ошибки

При получении `HTTPError` с кодом 401 начинается процесс обновления. Все остальные HTTP-ошибки (403, 404, 500 и т.д.) немедленно превращаются в `RuntimeError`.

**Строка кода:** `oauth_client.py:102-104`

### Шаг 2: Вызов refresh

Метод `_refresh_auth()` выполняет стандартный OAuth2 `refresh_token` grant:

**Endpoint:** `https://oauth.bitrix24.tech/oauth/token/`

**Параметры (URL-encoded form):**
- `grant_type=refresh_token`
- `client_id` — из конфигурации
- `client_secret` — из конфигурации
- `refresh_token` — текущий refresh-токен

**Строки кода:** `oauth_client.py:50-72`

### Шаг 3: Merge стратегия

Ответ от Bitrix24 содержит новые токены, но может **не** содержать служебные поля (`client_endpoint`, `domain`, `member_id`). Поэтому используется merge:

```python
refreshed = AppAuth.from_mapping({**asdict(auth), **data})
```

Старый `auth` распаковывается первым, ответ `data` перезаписывает только токены. Результат — объединённый объект со всеми полями.

**Строка кода:** `oauth_client.py:70`

### Шаг 4: Сохранение

Обновлённый auth немедленно записывается в файл через `auth_store.save()`:

**Строка кода:** `oauth_client.py:71`

### Шаг 5: Повтор запроса

Оригинальный запрос повторяется с новым `refreshed.access_token`. Если повтор тоже завершается ошибкой — выбрасывается `RuntimeError`.

**Строки кода:** `oauth_client.py:105-131`

---

## Однократный retry (не цикл)

Обновление токена выполняется **ровно один раз**. Если после refresh запрос повторно возвращает ошибку, это считается фатальной ошибкой.

Причины такого решения:
- Если refresh токен невалиден — повторный refresh не поможет
- Если проблема на стороне Bitrix24 — бесконечный retry усугубит ситуацию
- Приложение должно быть переустановлено в случае утраты токенов

---

## Поведение при ошибке refresh

Если `_refresh_auth()` выбрасывает `RuntimeError` (невалидный refresh token, сетевая ошибка, невалидный ответ), ошибка всплывает через `call()` в вызывающий код.

В контексте webhook-обработчика это приводит к HTTP 500.

---

## Потокобезопасность

`AppAuthStore` использует `threading.Lock` для защиты чтения/записи файла токенов. Если одновременно:
- Обработчик читает токен (`auth_store.load()`)
- Refresh обновляет токен (`auth_store.save()`)

Lock гарантирует, что операции не пересекутся на уровне файла. Однако между чтением и использованием токена в REST-запросе Lock не удерживается — это допустимо, потому что:
- 401 ошибка обрабатывается через refresh
- Два одновременных refresh приведут к одному результату (оба сохранят актуальный токен)
