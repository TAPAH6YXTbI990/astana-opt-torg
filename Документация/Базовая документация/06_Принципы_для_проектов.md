# Главные принципы для следующих проектов

## Архитектурные принципы

### 1. Единая точка входа
Всё приложение инициализируется через одну фабричную функцию (`create_app()`). Это упрощает тестирование, замену зависимостей и понимание структуры приложения.

**Правило:** Одно приложение — одна фабрика. Не создавайте FastAPI-инстансы в произвольных местах кода.

### 2. Разделение ответственности
Каждый модуль отвечает за одну конкретную область:
- Конфигурация — отдельный модуль
- Клиент API — отдельный модуль
- Бизнес-логика — отдельный модуль
- Модели данных — отдельный модуль

**Правило:** Если модуль делает больше одной вещи — разделяйте его.

### 3. Dependency Injection через параметры
Зависимости (клиенты, хранилища, настройки) передаются в обработчики через конструктор, а не создаются внутри. Это делает код тестируемым и гибким.

**Правило:** Обработчик не должен сам создавать клиента или читать конфигурацию — он должен получать их снаружи.

### 4. Конфигурация через переменные окружения
Все параметры, которые могут изменяться между средами (development, staging, production), задаются через `.env`, а не захардкожены в коде.

**Правило:** Никаких магических строк в коде. Конфигурация — в `.env`.

### 5. Явное управление аутентификацией
Токены хранятся в отдельном файле, управляются через отдельный класс, автоматически обновляются. Не нужно думать о токенах в бизнес-логике.

**Правило:** Аутентификация — это инфраструктурный слой. Бизнес-логика не должна знать детали получения токенов.

## Принципы кода

### 6. Типизация
Используйте аннотации типов во всех функциях и методах. Это упрощает чтение кода, поиск ошибок и поддержку IDE.

**Правило:** Каждая функция имеет типизированные параметры и возвращаемое значение.

### 7. Dataclass вместо dict для структурированных данных
Если данные имеют фиксированную структуру — используйте `dataclass`. Словари (`dict`) — только для полностью динамических данных.

**Правило:** Фиксированная структура = dataclass. Динамическая структура = dict.

### 8. Логирование с контекстом
Каждое логическое событие логируется с набором связанных данных (context). Логи должны содержать достаточно информации для воспроизведения ситуации.

**Правило:** Лог должен содержать: событие, входные данные, результат. Не логируйте секреты.

### 9. Санитизация секретов в логах
Любые данные, содержащие токены, пароли и ключи, замаскировываются перед записью в лог. Используйте единый механизм маскирования.

**Правило:** Если данные могут содержать секрет — прогоняйте их через `_sanitize_for_log()` перед логированием.

### 10. Обработка ошибок на границе
Исключения перехватываются на границе модуля (в webhook-обработчике), логируются и превращаются в понятный HTTP-ответ.

**Правило:** Внутри модуля — пусть исключение летит наверх. На границе — перехватывайте и возвращайте осмысленный ответ.

## Принципы безопасности

### 11. Проверка секретов входящих запросов
Каждый входящий webhook проверяется по секрету в URL. Невалидный секрет → 404 (не 401 или 403, чтобы не раскрывать факт существования эндпоинта).

**Правило:** Невалидный секрет = 404 Not Found.

### 12. Изоляция токенов приложения
Токены приложения хранятся в файле, который не попадает в git. Файл автоматически создаётся при установке приложения.

**Правило:** `.env` и файлы токенов — никогда в репозитории. `.gitignore` должен содержать их.

### 13. Минимальные права доступа
Бот использует только те методы API, которые необходимы для его работы. Не запрашивайте лишних разрешений.

**Правило:** Запрашивайте только то, что реально используется.

## Принципы работы с Bitrix24

### 14. Идемпотентность через дедупликацию
Одно и то же событие может прийти несколько раз. Используйте механизм дедупликации, чтобы обработать его только один раз.

**Правило:** Любая операция, которая может прийти повторно, должна проверяться на дубликат.

### 15. Два типа клиентов для разных задач
- **Webhook-клиент** (BitrixClient) — для вызовов от имени бота через REST webhook
- **OAuth-клиент** (OAuthBitrixClient) — для вызовов от имени приложения с токенами

**Правило:** Не смешивайте webhook и OAuth вызовы в одном клиенте.

### 16. Автоматическая привязка событий
При установке приложения автоматически привязывайте необходимые события. Не требуйте от пользователя ручных шагов, если это возможно автоматизировать.

**Правило:** Автоматизируйте настройку при первой возможности.

## Принципы развития проекта

### 17. Модульность = заменяемость
Каждый компонент должен быть легко заменяем. Если завтра появится лучший клиент для Bitrix24 — замена не должна затронуть бизнес-логику.

**Правило:** Пишите код так, как будто завтра каждую деталь нужно будет заменить.

### 18. Простота优先 (простота прежде всего)
Начинайте с минимально работающего решения. Не усложняйте архитектуру до реальной необходимости. Каждое усложнение должно оправдываться конкретной задачей.

**Правило:** Решайте проблему, которая существует сейчас, а не ту, которая может возникнуть когда-нибудь.

### 19. Документируем то, что не очевидно
Сложные бизнес-правила, неочевидные ограничения API, архитектурные решения — всё это документируется. Очевидный код не комментируется.

**Правило:** Комментарий должен отвечать на вопрос «заччем?», а не «что делает?».

### 20. Тестируемость как требование
Код должен быть написан так, чтобы его можно было легко тестировать. Внедрение зависимостей, чистые функции, минимальные побочные эффекты — всё это способствует тестированию.

**Правило:** Если функцию сложно протестировать — значит, она написана неправильно.
